# Logic：完整研究与可核查的研究过程

## 持续专业能力：完整清晰的结论型分析

本阶段的持续目标是形成完整、清晰、有解释力的分析。先理解公司及其问题，
以有依据的实质结论和判断组织研究正文，使段落推进读者对业务、价值、表现
及成立条件的认识。必要机制、事实、比较、反证和未知支持这些认识；不强行
断言，也不规定结论、理由、证据的固定数量或排列。

研究问题、核查方法、分析框架及执行步骤是获得分析的手段，记录在独立过程
材料中；它们不替代报告段落所说明的实质结论。写完后沿正文检查读者实际能
理解什么、为何如此及还有哪些边界，避免报告只描述“将如何分析”。完整研究
覆盖与证据要求仍适用，不提前写PPT页序，具体引用或算式修复留作实例。

## 研究工作

从用户的研究目标出发提出暂定问题，实际阅读原始资料并建立研究对象的范围及关系。资料可能改变问题、分类、判断和重点；不能只摘取支持最初框架的语句。按理解需要调查，保持不同产品、使用者、购买者、渠道和时期等差异；具体对象由实际题材决定，不预设行业问题清单。

补足能够由证据回答的问题，核对定义、单位、时期、主体、计算及因果范围。相反证据既用于挑战判断，也用于挑战研究框架。区分来源事实、计算、解释、公司归因、条件性判断和未知，不用通用机制填补具体资料没有支持的原因。

先形成展开的研究报告，再根据需要给摘要或索引。报告中的自然段、主题和层次来自实际论证；不提前承担PPT分页、页数、页面标题、栏位或固定分组。没有固定的发现数量、段数、字数或研究对象配额。完整性由用户目标、资料揭示的题材及必要解释共同判断。

过程文件保存实际检索与阅读、来源定位和摘录文件、口径比较、计算、发现的冲突、问题修订、补证及限制等可核查记录。记录可观察行动、证据和实质决定，不用“已充分研究”等宣称代替发生过的工作。

## 文件产物与交接

在任务目录内分别保存：

- `logic/research-report.md`：完整研究正文，包含必要证据和出处。
- `logic/research-process.json`：实际工作的events；每项有action、事实记录record，必要时附source_ids和实际证据文件引用。
- `logic/evidence.json`：来源与定位，保留实际取得的证据文件引用。
- `logic/data.json`：原始数值、口径、计算及出处；无数量研究时可以为[]。
- 本阶段角色清单：report、process、evidence、data各对应一个实际文件绝对路径。协调者另存该JSON并调用当前commit，工具保存stage-interface与不可变快照；作者不另造旧stage-files handoff。

作者直接保存上述真实文件。协调者执行`workflow_cli.py commit --run RUN --stage logic --files ROLE_FILES_JSON`；核心继续调用validate_research_documents校验报告、过程、来源与数据，不以跳过旧wrapper为由省略这些文件。工具不生成研究结论、不规定报告章节、不代作者批准质量。缺少报告或过程文件的findings列表不能作为研究交付。

协调者在run中保存task-config、workflow-rules、真实环境回执和训练绑定。Logic与Copy作者不接收含配置的旧技术运行包；Copy只消费project投影的完整report。保留身份、哈希与原生校验，不把监督记录塞回研究报告。

## 专业复核

专业复核核对是否完成课题、必要对象与关系是否展开、限制是否与判断相称。不能用findings ID、文件存在、来源数量或schema通过证明研究充分。normal/train的内容读者在Copy后先独立理解、再对照本报告；仅其真实repair可打开一次回Logic，补实质研究并重做受影响下游，保留失败与原读者复看。Auditor只记录，不另开返工。

普通制作不扩展为训练批次。为后续方法迭代保留本次真实输入、版本、报告、过程与异常；本次公司内容及案例修法不成为下一题的默认方法。

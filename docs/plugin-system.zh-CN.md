# 本地插件系统

本地插件在现有五个演示阶段周围增加三种入口：资源检查、讨论式知识学习和
PPT 赋能。它不增加第六个阶段，不声称已经连接 ChatGPT Library，不部署服务器、
发布包，也不包含治理内容或所有者私有内容。

## 入口模式

使用 `scripts/plugin_cli.py` 作为本地入口。命令包括：

- `inspect` 检查已安装组件、可用的 Library 快照和工具定义。它是只读操作，不是
  生产预检，也不会生成检索回执。
- `draft` 准备不可变的讨论审阅对象。对象记录会话、标题、负责阶段
  （`logic`、`copy`、`art-direction` 或 `output`）、共识、适用范围、限制、来源类别
  （`source-fact`、`user-experience` 或 `joint-inference`）、证据引用、未解决问题、
  语言、用途标签和附件。
- `confirm` 将实际用户的决定绑定到精确的 draft 摘要，包括附件元数据和哈希。它
  记录用户决定，不是用户身份的密码学证明；达成一致也不会把解释变成外部验证事实。
- `commit` 仅在确认后保存不可变版本。每个新版本显式记录父版本。知识、确认、附件
  元数据与哈希以及现有格式的 Provider 索引必须作为一个完整且已验证的快照一起发布。
  draft 或附件发生变化必须重新确认；失败、并发或父版本过期的写入要保留上一个快照
  可用。存储不可用时应报告不可用，不能伪装成空的成功 Library。
- `retrieve` 委托现有 Index，并返回来源与快照证据。draft、未确认共识和不完整快照
  不得进入检索。
- `read` 根据记录 ID 读取一个已验证的共识版本及其来源附件定位；不能读取 draft 或
  不完整快照。
- `tools` 列出现有的生产方法和代码入口。

每个附件都有稳定 ID、文件名、SHA-256、来源、权利和（已知时）页码/章节定位。明确
确认但没有外部证据的讨论可以没有附件；这种缺失必须保持可见。未解决问题只能作为
上下文，不能输出为已达成知识。所有者内容留在插件根目录之外，并通过受治理的
`library://` 绑定访问。

## PPT 赋能

能力或路径问题可以使用 `tools` 和 `inspect` 得到有用答复，而无需开始制作演示文稿。
当用户要求创建、修改或审计 PPT 时，Supervisor 运行现有的资源盘点、验收、预检和
证据锁，然后按原有的
`Logic -> Copy -> Art Direction -> Output -> Supervisor` 职责执行。已确认并提交的知识
可以通过现有 Index 选择使用，并保留其来源类别、证据限制、未解决问题和附件哈希。
任何阶段都不创建或提交讨论记录。

Output 继续使用现有的可编辑对象和渲染 QA 路径。资源检查不是生产批准，提交的讨论快照
也不会自动要求生成 PPT。

## 本地使用

在插件根目录用 Python 运行 `python scripts/plugin_cli.py --help`。
使用 `requirements.txt` 声明的依赖。`inspect --store ../owner-library`
检查外部持久 Library；`tools` 展示随包的制作方法及代码入口。

助手负责准备内部 JSON。你审阅的是可读的共识、适用范围、限制、来源和附件清单。
确认必须针对这份具体草稿；修改后需生成新的草稿与确认文件。原会话新修订的
`supersedes` 填上一个已入库草稿的 `draft_sha256`，独立会话填 `null`。

完整命令见[英文操作示例](plugin-system.md#local-command-example)。示例中的
确认标志不能代替你的实际决定。检索请求沿用
`packages/contracts/retrieval-request.schema.json`；返回的 Provider ID 和索引路径
可交给现有 `scripts/index_runtime_cli.py` 做明确选择与回执定稿。
整个任务固定同一快照，采用前用 `read` 读取实际共识及相关附件。

## 开发验收

实现必须保留基线测试，并覆盖 draft 排除、精确哈希确认、附件漂移、失败与并发提交、
过期父版本、快照复用与篡改、进程重启后的持久性、现有引擎检索、存储不可用、四个知识
归属阶段、公开/私有边界以及本地包闭包。合同测试不能证明模型判断或视觉质量。

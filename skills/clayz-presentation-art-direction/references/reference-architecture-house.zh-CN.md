# 参考架构房子图

本协议用于能力房子图、企业总体架构、数据或 AI 平台全景图和经营系统架构。它属于 `strategy-deployment` 下的页面原型，不是第五类材料路线。

## 先研究，再动笔

当用户要求广泛对标时，必须先建立指定规模的样本池。若用户要求研究 50–100 份资料，应计数 50–100 个确实包含架构图的独立文档或页面，不能把一个图库入口当成多份资料。

1. 优先使用官方架构中心、可部署参考架构、设计指南和技术文档；二手图库只能用于寻找一手来源。
2. 覆盖多个独立发布者与架构家族：数据平台、分析、AI 或 Agent、治理、安全、运营以及混合基础设施。若某一厂商因领域特殊性占据多数，要记录例外原因。
3. 在任务本地登记标题、发布者、链接、访问日期、架构目的、结构语法和采纳决定。
4. 学习关系，不学习像素：结果放置、层次顺序、横切控制、边界、流向、反馈、责任和视觉层级。
5. 明确 `never_copy`：品牌、母版、主题、产品图标、原文、媒体和坐标均不得复制。
6. 在讲者备注或来源记录中引用有代表性的一手资料；若方法或工具需要公开发布，应在公开来源文件中感谢被参考材料的作者与设计团队。

不得把下载的架构图打包进仓库，也不得复刻厂商产品栈。研究样本是独立综合的证据，不是模板库。

## 房子图合同

强房子图必须让架构一眼可检验：

| 结构角色 | 必须表达 | 失败信号 |
|---|---|---|
| 屋顶 | 业务结果、决策闭环或经营承诺 | 只有泛化技术标题 |
| 内部楼层 | 从来源到使用的有序能力转换 | 等权名词层，没有依赖 |
| 支柱 | 真正横切多个楼层的控制 | 治理只作为一次性装饰标签 |
| 地基 | 基础设施与运行底座 | 把云产品当成全图主角 |
| 上行路径 | 数据如何成为意义、证据、判断和行动 | 箭头暗示因果，却没有机制 |
| 回流路径 | 结果、纠正和例外如何修订系统 | 没有反馈、版本、审批或回滚 |
| 责任边界 | 模型可以建议什么、人必须决定什么 | 把组织责任静默让渡给 AI |

面对 ChatBI 或企业认知系统，还要额外检查四项：

- 用户体验与行动位于推理机器之上。
- 调查编排独立成层：情境、假设、工具、反证、不确定性和停止条件。
- 把业务语义表达成可执行现实：对象、关系、指标、维度、粒度、生效时间、证据、来源与责任。
- 把反馈表达成受控生产流程：质疑、归因、专家裁决、回归、版本发布、效果追踪和回滚。

## 构图规则

1. 从空白主题或用户批准的主题开始，绝不导入研究来源的母版。
2. 让屋顶、楼层、支柱和地基承担不同视觉职责，不能仅靠加粗边框伪造结构强度。
3. 使用一条主上行路径和一条明确回流路径；先画连接关系，再放房间，保证连线可读。
4. 每层只保留足以证明其职责的少数能力；实施细节放进备注或后续页面。
5. 默认使用原生可编辑形状；只有具备必要语义角色且权利可追溯的用户批准资产才能进入。
6. 保持管理阅读顺序：先结果，再转换，再控制，最后才是实施技术。
7. 按整页尺寸渲染，拒绝文字裁切、支柱碰撞、微型文字、连线歧义和装饰性留白。

## 否决测试

出现以下任一情况，页面不得批准：

- 只换标题就能套用到任何公司。
- 观众说不清某一层为什么位于另一层之上。
- 治理、安全、质量或可观测性没有真正约束相关楼层。
- 反馈路径止于“再训练”，没有证据归因、人工裁决、版本和回滚。
- 产品名称多于业务能力。
- 图中隐藏不确定性，或让模型看起来在替组织承担责任。
- 页面更像某一张厂商参考图，而不是当前问题的独立表达。

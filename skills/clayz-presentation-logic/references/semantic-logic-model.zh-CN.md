# 页面语义逻辑底稿

## 目的

先证明“内容为什么这样分”，再交给下游决定“页面怎样画”。三层或四层消息树只说明展开深度，不证明分类正确；本底稿专门拦截对象混级、关系误判和方法链缺失。

## 一、先写无视觉词逻辑句

每个正文页先写一句不换行的逻辑句：

> 谁／什么，通过什么机制，与哪些同级对象形成什么关系，最终产生什么结果或行动含义。

句中不得出现“左边、右边、上方、下方、圆圈、框、卡片、箭头、环绕、颜色”等视觉词。若一句话说不清，先拆清业务关系或回流拆页，不能先选图形。

Copy会把这条逻辑精炼为受众可见的标题和Storyline；Logic只锁定语义句，不预先决定最终措辞和断句。

## 二、业务对象辨型

为每个对象选择最具体的语义类型：

| 类型 | 识别问题 | 例子 |
|---|---|---|
| `channel-carrier` | 谁承接交付或触达动作 | 在线入口、线下触点、服务团队 |
| `method` | 用什么方法把输入转为结果 | 引导上手、需求识别、功能采用 |
| `principle` | 哪条原则约束方法 | 先建立首个价值，再扩大使用 |
| `product` | 用户购买或使用什么产品 | 入门版、团队版、企业版 |
| `project` | 哪个专项组织资源和动作 | 上手优化、留存实验 |
| `scene` | 用户在什么真实情境中出现 | 首次登录、多人协作文档 |
| `entry-method` | 以什么方式切入引导或服务 | 产品内引导、上手问题清单 |
| `exception` | 正常路径之外如何处理 | 用户只需要单一功能 |
| `user-segment` | 面向哪类用户 | 新用户、团队管理员 |
| `need` | 用户想解决什么 | 快速上手、跨团队协作 |
| `risk` | 需要识别或管理什么不确定性 | 隐私风险、可用性风险、采用风险 |
| `role` | 谁负责或协同 | 顾问、专员、执行团队 |
| `action` | 主体具体做什么 | 提问、登记、跟进 |
| `capability` | 需要什么稳定能力 | 数据识别、专业履约 |
| `resource` | 方法运行依赖什么 | 数据、工具、预算 |
| `metric` | 如何衡量 | 激活率、周留存率、协作深度 |
| `result` | 最终形成什么结果 | 稳定采用、持续留存 |
| `stage` | 真实时间或成熟度阶段 | 注册、激活、协作 |

无法落入以上类型时使用 `other`，并在对象标签中写清业务定义；不得用“其他”掩盖未完成的理解。

## 三、同级与父子校验

- 同一同级组的成员必须是同一种语义类型、同一粒度并共享同一父对象。
- 产品不能与项目、交付路径、方法、场景、切入方式、异常处理或结果并列。
- 场景、切入方式和异常处理必须分开：发生了什么、主动怎么进入、偏离正常路径后怎么办，是三类不同对象。
- 若A统领B/C，A是父对象，B/C才是同级子对象；不要把统领句与枚举项平铺。
- “入门版、专业版、团队版、企业版”可共同归入“覆盖不同规模的协作需求”；后者是上级结果或主张，不是第五个并列产品。
- 四项需求若互不导致对方，记录为等权并列；没有方向就不写先后、循环或连接关系。

## 四、关系语法

仅使用能够被业务语义证明的关系：

- `peer`：同级等权，无方向；
- `contains`：整体包含部分；
- `supports`／`enables`：工具、能力或资源支撑方法与结果；
- `maps-to`：用户群、需求、风险、动作或产品逐项对应；
- `sequence`／`transforms-to`：存在真实先后或状态变化；
- `cause`：证据足以支持因果；证据不足时降为假设；
- `condition`：只有满足条件才进入路径；
- `feedback`：结果返回并影响前序环节；
- `contrast`：对象按同一维度比较；
- `exception-to`：异常或边界限定正常路径；
- `evidence-for`：事实、数据或案例支撑判断。

并列对象不写连接方向；映射不自动等于流程；环绕不自动等于循环；编号不自动等于先后。

`condition` 必须通过 `combination` 说明组合方式：`all-of`（全部成立）、`any-of`（任一成立）或 `one-of`（互斥选择），并在 `logic_map.statement` 与 `do_not_change` 中写成人能复述的约束，例如“产品与用户阶段两项条件同时成立，不得改写为先后步骤”。共同条件不是 `sequence`，阅读顺序也不是业务顺序。

### 状态变化的四段合同

`transforms-to` 不是“旧／新”左右并列。必须能回答：

1. 旧约束或旧激励为何不够；
2. 改了哪条规则、资源或责任；
3. 规则变化将怎样改变具体行为；
4. 行为变化带来什么结果，在什么对象和例外范围内成立。

缺少第2或第3段时，不得用状态转换关系；改用 `contrast` 并明确只是同维度比较。

## 五、方法链

方法、SOP、经营原则和动作页必须逐项回答：

1. **触发什么**：用户信号、使用情境或前置条件；
2. **做什么**：主体采取的动作或提问；
3. **识别什么**：需求、风险、差距或机会；
4. **对应什么**：产品、服务、责任或下一动作；
5. **如何收口**：结果、承诺、边界、跟进或转化。

例如“三问”不能停在三个问题本身，应写成逐行映射：`怎么问→识别什么需求或风险→对应什么功能或动作`。若某环确实不存在，说明任务理由并回查该页是否仍应被定义为方法页。

## 六、经营系统与试验学习

### 可运行性测试

地图、模型、机制和“看板—例会”类页面只有同时具备以下要素，才能定义为 `operating-system`：

- 输入：数据、用户群、信号、问题或任务；
- 判断规则：如何分类、比较、触发或取舍；
- 输出：生成什么动作、决策、责任或资源配置；
- 使用者：谁在什么场景使用；
- 节奏：多久更新、在哪个会议或动作周期使用；
- 反馈：结果如何返回并改变下一轮输入或规则；
- 例外：什么情况不适用或需要人工判断。

缺少其中关键项时，称为“分类框架”“关系模型”或“静态地图”，不要夸大为操作系统。

### 试验学习合同

项目复盘优先建模为：`hypothesis → intervention → observation → disconfirmed_belief → new_learning → next_test`。观察结果不等于学习；只有说明哪条认识被保留或推翻，才能进入下一轮验证。

## 七、跨页不变量与原子化交接

同一用户群、产品、角色、指标或政策对象跨页出现时，先声明语义不变量：名称、定义、顺序、口径、分析轴和分组中的哪些必须保持。连续页再声明每页新增的证据、层级或动作。Logic不指定视觉同构，但必须让Art Direction知道何处改变会破坏比较，何处重复没有业务理由。

- 每个节点只表达一个语义职责，不用 `|`、`｜`、连续空格、冒号串联或手工换行模拟下级。
- 编号关系只在真实步骤或排名成立时写入语义关系；普通并列记录为 `peer`。
- KPI在Logic中分别识别指标、值、单位、期间与基准，便于Copy生成原子文案。
- 同一兄弟组的对象类型、粒度和分解维度一致；无法形成平行文案时先在Logic重构。
- 边界、话术底线和来源作为独立逻辑节点或来源字段，不混入主判断。

## 八、交接前复述测试

逐页遮住所有视觉设想，仅凭逻辑底稿回答：

1. 这一页最重要的方法、判断或证据是什么？
2. 一级分类是否同类、同粒度、共同支撑主判断？
3. 每个二级说明归属哪个一级对象？
4. 哪些关系有方向，哪些只是并列或包含？
5. 若是方法页，五段方法链是否完整？
6. 若是From／To，旧约束、规则、行为和结果是否完整？
7. 若是经营系统，输入、规则、输出、使用者、节奏和反馈是否齐全？
8. 若属于系列页，哪些对象必须不变、这一页新增了什么？

任一问题答不清，不得进入页内消息树和下游表达设计。
